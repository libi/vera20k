# RFC 0001 参与者建议与待定事项

上游草案 PR #4653 由 **libi** 提出，讨论 MOD 和地图怎样用 Wasm 扩展规则、触发和界面。PR 说明仍写 0.0.13，本页以所链接提交中的 **0.0.14** 正文和 API 附录为准。上游将这次 PR 用于征求反馈，RFC 的接受和功能开发另行决定。本页给每位参与者保留原帖入口，按原文节号登记建议，供开发和复查时引用。[草案 PR](https://github.com/YuriPlanet/vera20k/pull/4653) · [中文正文](https://github.com/libi/vera20k/blob/b6cd01ff8e90aad4ab55e28a79bfda520c4f30f9/docs/rfcs/0001-wasm-extension-modules.zh-CN.md) · [中文 API 附录](https://github.com/libi/vera20k/blob/b6cd01ff8e90aad4ab55e28a79bfda520c4f30f9/docs/rfcs/0001-wasm-extension-modules-api.zh-CN.md)

## HaoJun0823 的内容包与制作工具建议

原帖附中英文全文、完整 INI 和目录示例。HaoJun0823 支持 RFC 关于模拟确定性、客户端权限和执行预算的方向，同时提出内容包的组织方式。下表保留其原文各节的范围。其中 `[VeraPatch]`、清单字段和工具命令均为作者提案。[HaoJun0823 的完整建议](https://github.com/YuriPlanet/vera20k/pull/4653#issuecomment-7040998846)

| 原帖章节 | 建议及适用条件 |
|---|---|
| 1 · 总体方案 | 保留 RA2/YR 的 INI 制作流程，在其上建立统一的内容包身份、类型目录和加载阶段。Wasm 承担数据难以表达的行为。沿用已有 INI 工具与 `mod.ini` |
| 2 · 基础游戏作为内容 | RA2、YR、自定义基础游戏和大型全转换 MOD（TC）可以分别选用各自的规则、界面和所需资源。通用素材通过显式依赖共享。DLC 体系可推后。《心灵终结》是全转换包的例子，原素材授权和引擎能力仍须逐项满足。原帖以 Skyrim、Fallout、RimWorld 和 Mount & Blade 的基础内容组织为参照 |
| 3 · 模块化 INI | 将单位、武器、国家等拆成独立 INI，保留 `Cost`、`Strength`、`Primary` 等原字段。普通规则用数据制作，复杂 AI、攻击、任务链与界面可用 TypeScript 或 Rust 编译成 Wasm。两种作者入口长期共存 |
| 4 · 显式修改 | 用 `[VeraPatch]` 声明类型目录和对象 ID。`Add` 新增并登记，`Merge` 仅改列出的字段，`Replace` 替换整项并检查必填字段，`Remove` 区分删字段、删集合成员和删类型。删除后检查地图、AI 和生产队列等引用。加载器生成内部编号。原帖分别讨论 FAF、RimWorld、Bethesda 与《文明 VI》的合并或覆盖语义 |
| 5 · 清单和权限 | 扩展现有 `mod.ini`，可声明 UUID、命名空间、包类型、目标、依赖、冲突及先后顺序。`Needs` 继续表达最低引擎版本。允许任意文件名的多个 Wasm 模块，由清单、模块元数据及实际导入权限认定模拟、客户端或混合内容。仅界面包须经过验证 |
| 6 · 本地化预加载 | 扫描清单后先读取当前语言的元数据，MOD 管理器即可为尚未启用或依赖缺失的包显示名称、说明及错误。随后解析依赖、预检并加载。`NameKey`、`AboutKey` 和 `[Localization]` 配合当前语言、默认语言、原文三级回退。限制文本大小、编码与包内路径。纯显示文本独立于模拟哈希 |
| 7 · 字典、SDK 与 AI 辅助 | 以机器可读 INI 字典声明类型、数值范围、引用和补全，可参考社区 RA2-INI-Dictionary。内容工具提供来源检查、依赖分析与打包，Wasm SDK 提供宿主 API、事件及编译工具。AI 可按相关文件和字典拆分旧配置，输出仍经过同一套验证 |
| 8 · 界面和扩展生命周期 | 参照 RA3 AptUI，将渲染、布局、输入交给引擎，内容包提供菜单、选阵营、侧栏、HUD 和战役画面，引擎保留启动与恢复界面。可结合静态布局和客户端 Wasm。参考 FAF 的 Hook/schook 和 Forge，区分发现、依赖求解、预检、注册、读规则、初始化、对局七阶段，回调数量可另定 |
| 9 · 地图作为任务包 | 地图可携带剧本、Wasm、任务专用单位、EVA、语音、音效、音乐、UI 和译文。类型目录优先沿用步兵、车辆、飞机、建筑、国家／阵营、武器／弹头等社区名称，再扩展战役、音画、界面和翻译。EVA 事件和音频可以直接用 INI 映射 |
| 10 · 联机有效内容哈希 | 按实际生效的规则、地图、模拟模块、依赖与顺序计算内容摘要。清单里影响模拟的 `[RuleFiles]` 和排序也参与。仅界面资源和说明文字可由玩家独立安装。相同摘要之外，还需保证 Wasm 执行确定性 |
| 11 · 附录 A，比奇堡阵营包 | 完整目录和清单展示中英文元数据、指定文件顺序、国家 `BIKINI`、步兵 `SPONGE`、武器 `SPATULA`、侧栏和任务。沿用已有 Side 即可增加 Country，独立 Side 需要额外引擎能力。示例分别声明战斗与侧栏模块。最终加载顺序由清单和依赖决定 |
| 12 · 附录 B，迁移现有 MOD | 比对旧 `rulesmd.ini` 与原版，从 E1 提取有改动的字段，用 `Merge` 登记，再由 `[RuleFiles]` 引用。新增单位用 `Add`，同时检查武器和动画依赖。工具可提供 `vera mod validate`、`vera mod diff` 及 AI 迁移 Skill。对照最终规则和场景结果。建议由清单显式启用模块化，长期支持传统 INI、模块化 INI、含 Wasm 的高级 MOD |
| 13 · 希望 RFC 回答的问题 | Wasm 的模块来源、规则叠加、ABI 和初始化能否为模块化 INI、统一类型目录及可编程扩展留下接口？保留渐进兼容，根据实际玩法分阶段实现 |

## libi 对内容包建议的回复

1. **原有内容入口。** libi 表示，按 RFC 的设计，RA2 原有 MOD 的 INI 可继续使用。草案在此之上增加动态修改 INI 和调用 AI 脚本等配置的能力。这里记录的是作者对草案兼容目标的答复。独立 fork 的兼容清单仍按产品、版本和场景验收。
2. **同时启用多个 MOD。** libi 转述资深 MOD 作者对作品二次分发的顾虑，建议暂缓在上游接入多 MOD 共存。HaoJun0823 对依赖、先后顺序和冲突的提案仍保留，双方对交付时机有不同考量。
3. **分期实施。** libi 赞同渐进实施，建议把 RFC 拆成多个子阶段。草案正文列出的顺序是模拟模块、客户端模块、实际任务与外部作者试用，再讨论版本 1 冻结。[libi 的回复](https://github.com/YuriPlanet/vera20k/pull/4653#issuecomment-7042992589) · [草案实施阶段](https://github.com/libi/vera20k/blob/b6cd01ff8e90aad4ab55e28a79bfda520c4f30f9/docs/rfcs/0001-wasm-extension-modules.zh-CN.md#L850-L856)

## EncoreAlpha 的可组合 INI 建议

EncoreAlpha 提议将 RA2、YR 和 Ares 分别做成预设，共用运动、命中、伤害和规则执行。地图作者保留 FA2 的事件、动作与 Tag。新规则使用具名节，由单位或地图按名引用。对 `[E1]` 受伤的例子，建议允许在 INI 内声明对象变量 `Panicked`。两个美国大兵各自首次满足条件时各记一次，保存再读取后继续沿用本单位的值。这同时给手写 INI 与织网者导出提供了一张验收图。[完整跟进建议](https://github.com/YuriPlanet/vera20k/pull/4653#pullrequestreview-6002534664) · [第 4 问行内讨论](https://github.com/YuriPlanet/vera20k/pull/4653#discussion_r4650283817)

## 上游与 fork 的接口取舍

| 事项 | 上游或参与者意见 | 独立 fork 的处理 |
|---|---|---|
| 旧 INI 与新玩法 | libi 提出兼容既有 INI，HaoJun0823 提出保留原字段并可拆文件 | 目标一致。旧注册编号保留给老地图，新定义按包名和节名发现。原版读序、版本差异和每条行为按兼容清单核对 |
| 包的注册和多个 MOD | HaoJun0823 提议显式注册操作和加载顺序。libi 建议暂缓多 MOD 共存 | 首批先验证选定预设、一个制作组的 MOD 和本局地图。`[VeraPatch]` 的四种操作、与 fork 的 `[Patch …]` 如何互导，以及跨制作组叠包，均保留讨论 |
| 模块分工 | 草案以 `rules.wasm` 与 `ui.wasm` 区分执行环境。HaoJun0823 建议支持多模块、显式角色及实际权限校验 | 首版交付手写 INI、模板和字典。后续 Wasm 接同一套事件与命令，文件名、模块数量和权限认定留给 ABI 设计 |
| 同帧连锁超限 | 草案将超限的触发留到下一帧，再检查过滤条件 | fork 提议结束本次根事件未执行的动作，继续其他来源。同一张反伤图会观察到不同的触发次数。共用运行结果前须选定语义或版本化 |
| 脚本失败 | 草案保留失败调用已经完成的写入，随后停用模块 | fork 提议在一次调用成功结束后提交其写入和效果请求。失败前已设变量的场景可区分两种结果 |

两套设计可以共享 INI 的作者入口。需要明确约定的是影响锁步、读档和旧 MOD 实际表现的语义。原作者提出的界面、翻译、工具链与多 MOD 方案继续列入对应主题。[路线图及验收](composable-gameplay-roadmap.md) · [草案的连锁处理](https://github.com/libi/vera20k/blob/b6cd01ff8e90aad4ab55e28a79bfda520c4f30f9/docs/rfcs/0001-wasm-extension-modules.zh-CN.md#L331-L337) · [草案的模块失败处理](https://github.com/libi/vera20k/blob/b6cd01ff8e90aad4ab55e28a79bfda520c4f30f9/docs/rfcs/0001-wasm-extension-modules.zh-CN.md#L260-L266)

## RFC 0.0.14 的 18 项待定问题

编号沿用原文，便于在 PR 中继续讨论。分组仅用于查阅，具体选项、预算候选值及建议的实验见草案原文。[全部待定问题](https://github.com/libi/vera20k/blob/b6cd01ff8e90aad4ab55e28a79bfda520c4f30f9/docs/rfcs/0001-wasm-extension-modules.zh-CN.md#L876-L895)

| 编号 | 待决定事项 |
|---|---|
| 1–3 | 1. 浏览器 Wasm 引擎或嵌入式解释器的性能与确定性。2. TypeScript SDK 的编译器及体积、速度、语言支持。3. 运算和调用深度计量、NaN 处理及 wasm32 状态哈希成本 |
| 4–6 | 4. 具名 INI、FA2 旧记录、筛选及原子动作的写法与键前缀。5. 新事件和动作的编号范围与扩展冲突。6. FA2 保存地图时是否保留未知 Wasm 节 |
| 7–9 | 7. 模块体积、内存、执行额度、队列、消息与事件上限。8. 模块所在帧阶段和弹体移动、碰撞、引爆的顺序。9. 模块内存写入快照的压缩与实际体积 |
| 10–12 | 10. 首批允许脚本同步决定结果的事件。11. 对局中可按类型动态修改的键和属性。12. 版本 1 提供的事件、动作、属性、修饰器与搜索范围 |
| 13–15 | 13. 修饰器的合成、叠层、刷新、互斥和 Phobos AE 对照。14. MOD／地图的界面布局位置、首版节点及本地设置属性。15. 地图模块文字的翻译来源 |
| 16–18 | 16. 战役换关时模块和变量是否延续。17. 每帧连锁深度和触发次数上限。18. 模块是否可接管一个电脑 House 的决策、大厅能否按座位选择 |
