# .vmod 设计

提案；此处内容尚未实现。

`.vmod` 是 VERA20K 的 mod 发布格式。mod 用普通的 INI 和资源编写，也可以部分用 WASM 代码编写，
最终发布为一个签名包。这个包有两个目标：

- **不能直接修改。** 改动过的包无法通过签名校验；改动过的 mod 无法加入用原版 mod 建立的房间、
  排位赛，也无法打开用原版 mod 制作的存档和回放。
- **提高提取门槛。** YR、XCC 等现有工具无法打开包；mod 的玩法逻辑以编译并混淆过的 WASM 发布，
  而不是可读的 INI。

WASM 是 VERA 的扩展运行时，相当于其他游戏里 Lua 的角色：mod 代码调用引擎接口来查询状态、
执行动作和响应事件。

## 目标与范围

范围内：

- 带签名的容器格式；
- 数据 INI 和核心资源在包内加密；
- INI 中的逻辑部分由打包器自动编译为 WASM，作者照常写 INI；
- 手写的 WASM 扩展调用同一套引擎接口，并可从 INI 调用；
- 面向多人对战、存档和回放的 mod 校验。

范围外：

- 阻止被修改过的引擎提取内容。引擎是开源的，改一行代码就能导出它解码的任何内容；
  见[威胁模型](#威胁模型)；
- 改变原版的读取路径或 rules 语义；
- 在包中附带原版文件；玩家仍需自备游戏文件。

一个 mod 就是多一个高优先级资源来源，加上一个逻辑模块。没有 mod 时，引擎的行为与现在完全一致。

## 威胁模型

| 攻击者 | 由什么阻止 |
| --- | --- |
| 用 XCC 或十六进制编辑器打开包 | 加密区段、哈希化的文件名 |
| 修改包后自己玩 | 挂载前的签名校验 |
| 带着修改过的 mod 与他人联机 | 房间、排位、存档和回放中的 mod 摘要 |
| 重新上传别人的 mod | mod 库的内容指纹和作者密钥 |
| 想读懂玩法逻辑 | 编译并混淆过的 WASM：反编译或试探都需要相当的工作量 |
| 修改引擎导出解码后的数据 | 技术上无法阻止；数据 INI 和资源可以这样读出 |

模拟在热循环里读取的数据无法隐藏。`src/sim` 读取 rules 值超过 4000 处，其中很多是逐单位、
逐 tick 的。每次读取都经过 WASM，就达不到 20,000 单位的目标；一次性交出这些值，它们就以明文
存在于引擎内存中。黑盒的取值函数也可以沿着引擎本来就持有的类型列表逐个枚举。逻辑则不同：
引擎只需要它的输入和效果，因此逻辑的结构和常量可以留在 WASM 内部。

## 包格式

`.vmod` 文件包含六个区段。

| 区段 | 内容 | 存储方式 | 引擎如何读取 |
| --- | --- | --- | --- |
| 头部 | `VMOD` 魔数、格式版本、区段偏移 | 明文 | 挂载时解析 |
| 清单 | id、版本、接口版本、所需能力、依赖、作者公钥、各区段摘要、逻辑导出 | 明文 TOML | 校验并按依赖排序 |
| 数据区段 | 数据 INI 和核心资源 | MIX 风格条目，压缩后用每次构建生成的密钥加密 | 挂载时解密一次，放入内存归档 |
| 逻辑区段 | `logic.wasm`：编译出的 INI 逻辑和手写扩展 | WASM，经过混淆 | 挂载时实例化，整局常驻 |
| 明文区段 | 非核心资源 | MIX 风格索引加未压缩正文；索引用包密钥加密 | 直接在文件上构建归档；桌面端使用内存映射 |
| 签名 | 对之前所有字节的 Ed25519 签名 | 明文 | 挂载前验证 |

包中不存储文件名。每个条目都以引擎查找文件所用的 MIX 名称哈希（`mix_hash`）为键。
数据区段的密钥随包一起分发，因此这层加密挡住的是现成工具，而不是下定决心的读取者。

## 资源分级

小型、mod 专属的资源放进数据区段；大型、通用的资源放进明文区段。除 INI 外，作者可以用通配符
调整任何资源的归属。

| 资源 | 默认区段 | 原因 |
| --- | --- | --- |
| 数据 INI：rules、art、ai（骨架）、sound、eva、theme 及模式 INI | 数据区段，固定 | mod 的核心设计 |
| INI 中的逻辑部分 | 编译进逻辑区段 | 见[逻辑编译](#逻辑编译) |
| VXL、HVA | 数据区段 | 新载具模型，体积小且 mod 专属 |
| 新单位、建筑和步兵的 SHP | 数据区段 | mod 专属美术 |
| 仅被上述资源使用的图标（SHP/PCX）和调色板 | 数据区段 | 体积小 |
| CSF 字符串 | 明文 | 价值低 |
| TMP 地块及其他地形主题资源 | 明文 | 文件多，大多派生自原版 |
| 音频（bag/idx、wav、aud）和音乐 | 明文 | 体积大 |
| BIK 视频、载入画面、大型 UI 美术 | 明文 | 体积大 |
| 原版文件 | 不打包 | 玩家自备 |

作者在项目文件 `mod.toml` 中覆盖默认设置：

```toml
[protect]
include = ["*.vxl", "*.hva", "units/*.shp", "cameo/*"]
exclude = ["*.wav"]
```

数据区段设有软上限，在测得浏览器版本数据前建议为压缩后 64 MB。超出时打包器发出警告，但不拒绝。
设此上限是因为该区段在挂载时一次性解码，而浏览器版本受 wasm32 内存限制。

## 数据 INI

数据 INI 以 INI 文本的形式交给引擎，原生读取器和 rules 分层不变。之所以用文本而不是解析后的值：

- 原生读取器掌管许多细节：511 字节截行、`;` 注释、`Key=` 视为缺失、键名区分大小写、
  重复键以第一个为准；
- 地图和模式 INI 会逐键覆盖 mod 的 rules 键，因此这些 rules 必须进入同一个分层栈；
- `RuleSet` 的内部布局会随引擎版本变化；文本在引擎更新后无需重新打包即可继续使用。

规范化：

1. 先按原生方式拆行：LF 结束一行，丢弃 CR，NUL 结束该行，且只保留前 511 字节。
   这样读取器看到的值与原文件完全一致。
2. 然后去掉注释、空行以及首尾空白。
3. 保留每个键，包括引擎尚未读取的键，这样日后移植的 Ares 和 Phobos 键仍能找到其值。
4. 保持区段和键的顺序；注册表按读取顺序分配类型。
5. 把每个已编译的逻辑条目替换为它的骨架（见下一节）。

文件名保持不变（`rulesmd.ini`、`artmd.ini`、`aimd.ini` 等），因此 `[ini] profile` 以及
RULESMD → LANGRULE → 模式 INI → 地图 的分层继续有效。mod 的 `rulesmd.ini` 按归档优先级
取代原版文件，与如今放在 `expandmd99.mix` 中的 INI 方式相同。

## 逻辑编译

### 两种来源，一个模块

- **INI。** 作者照常写 INI。`vmod build` 把其中的逻辑部分编译进 `logic.wasm`，不需要额外手写任何东西。
- **手写 WASM。** 需要更多能力的作者针对同一套接口编写 WASM（先提供 Rust SDK）。INI 通过保留编号
  调用这些函数：
  - AI 触发条件编号 1000 及以上，调用已注册的条件导出；
  - 脚本动作编号的一段保留区间，调用已注册的动作导出；
  - 地图触发的事件和动作以后沿用同样的模式。

两种来源链接成每个 mod 唯一的 `logic.wasm`，使用同一套 ABI。

### 编译即对引擎解释器做特化

引擎已经在解释由 INI 定义的逻辑：

| 解释器 | 解释的 INI |
| --- | --- |
| `condition_holds`（`src/sim/ai_team_creation.rs`） | `aimd.ini` 中的 `[AITriggerTypes]` 条件 |
| `team_script_vm`（`src/sim/team_script_vm.rs` 及其 `actions`、`super_actions` 模块） | `[ScriptTypes]` 动作列表 |
| `trigger_runtime`（`src/sim/trigger_runtime.rs`，`evaluate_event` 和动作分派） | 地图 Triggers、Events 和 Actions |

编译一个条目，就是把解释器的分派和该条目的常量折叠进代码。以"a > b 时执行 c"为例：WASM 通过
import 读取 a，与折叠进代码的 b 比较，再调用 c 对应的 import。引擎看到的只有接口调用。

叶子操作保持原位。计数己方单位、读取可用资金、执行一个队伍动作，仍然是引擎中该原生函数唯一的
Rust 实现，以 import 的形式暴露。WASM 只包含组合逻辑和常量，因此没有任何原生函数多出第二份实现。

```
INI --(引擎读取器)--> 定义结构 --> 逻辑 IR --> 混淆 --> wasm-encoder --> logic.wasm
                          |
                          `--> 骨架（id、引用、调度状态）--> 数据 INI
```

- **读取器。** 打包器用引擎自己的读取器把 INI 解析为引擎的定义类型，例如
  `TeamAiTriggerDefinition`，因此每个词法细节都与运行时一致。
- **IR。** 一个小型的表达式与序列 IR，例如 `Compare(op, Call(house_money, enemy), Const(5000))`。
  手写 WASM 不经过它。
- **骨架与逻辑。** 引擎保留其调度器要读写的内容；判断移到 WASM。以 `TeamAiTriggerDefinition`
  （`src/sim/team_script_vm.rs`）为例：
  - 骨架：id、`primary_team_type` 及其他队伍引用、`weights`（对局中会变化并写入存档）、
    `enabled`、`side`、`multiplayer`、`owner`；
  - 编译：`condition`、`comparison_mask`、`object_type`、`threshold`。
- **等价性。** 每个编译出的条目都必须与原生解释器做出完全相同的判断。`vmod build` 在一组构造好的
  状态上同时运行两者，任何差异都拒绝打包。
- **混淆。** 原版逻辑的形状是固定的：直接编译的结果反编译出来就是 `if house_money(e) > 5000`。
  由于编译是自动的，每次构建都可以用随机种子做常量拆分、不透明谓词和控制流平坦化，作者无需付出任何代价。

### 分层

地图会扩展 `aimd.ini`，也可能替换 mod 的触发或脚本。按 id 决定：被地图层替换的条目，用地图的定义
交给原生解释器执行；否则执行编译出的导出。一个 `[AITriggerTypes]` 值是一行 18 个 token，
所以替换总是整条替换，不会出现一半编译、一半解释的情况。

### 各类逻辑的保护程度

- **AI 触发条件** 隐藏条件、比较符、数量和计数的类型。要还原它们，需要反编译混淆过的 WASM，
  或用构造的游戏状态去试探。
- **脚本和地图触发动作** 大多是有序的引擎动作。步骤状态留在引擎中，所以逐步执行一个脚本就能看出
  它的顺序；编译隐藏的是条件参数和分支，而不是顺序。

## 扩展运行时

桌面端用 wasmtime（Cranelift）运行 `logic.wasm`；浏览器版本通过 `js-sys` 交给浏览器自带的
WebAssembly 引擎。两者都编译为机器码，所以一次钩子调用的开销约等于一次原生调用加上跨接口的开销。
两套引擎必须给出完全相同的判定，因此所有可能导致差异的东西，都在模块到达任一引擎之前被去掉。

- **编译与缓存。** 桌面端在 mod 安装或首次挂载时编译模块，并按逻辑摘要和 wasmtime 版本缓存在本地。
  引擎绝不加载不是它自己生成的预编译产物：wasmtime 的 `Module::deserialize` 信任输入，
  下载来的产物就等于任意原生代码。浏览器在挂载时用 `WebAssembly.compile` 编译。
- **指令检查。** 打包器和引擎都拒绝浮点、SIMD（包括 relaxed SIMD）以及线程/原子指令，
  且只允许来自接口列表的导入。剩下的是整数代码，任何符合规范的引擎运行结果都相同。
- **燃料与栈深度。** 限制由打包器插桩进模块，而不依赖引擎自带的计量：每个基本块从燃料全局变量中
  扣除自身开销，每次调用检查深度全局变量。两个引擎运行同一份插桩代码，所以 mod 在每个客户端上
  都在同一条指令处耗尽燃料。燃料耗尽时，该条目回退到原生默认行为并记录日志。引擎拒绝没有插桩的模块。
- **数值。** 只用整数：`i32`、`i64`、引擎句柄和 `SimFixed` 的原始位，与引擎的模拟数学规则一致。
- **运行时机。** 钩子只在串行的 tick 阶段运行（Triggers、TeamScript、AI 组队），绝不在 rayon
  并行阶段内运行，所以每个 mod 一个实例就够，wasm 多线程版本也不需要每个 worker 各建实例。
  调用按批进行：一次调用为一个阵营评估某阶段内所有已注册的条目，因此每 tick 跨接口的次数取决于
  阵营数，而不是条目数。这在浏览器中最重要，因为每次调用都要经过引擎 wasm 与 mod 实例之间的 JS 胶水。
- **内存与状态。** 内存很小，上限写在清单里，每批调用前重置为初始快照，所以模块内部不保留任何状态。
  状态放入归模拟所有的键值存储，因此会进入存档快照（`src/sim/snapshot.rs`）
  和同步哈希（`src/sim/world/world_hash.rs`）。
- **随机性。** 只能通过接口从对局的随机流获取；mod 没有自己的随机源。
- **语言。** 任何能生成不含浮点和 SIMD 的 wasm32 的工具链都可以对接这套接口；先提供 Rust SDK。
  运行时内部使用浮点的语言（大多数带垃圾回收的语言）过不了指令检查。

wasmi 这类解释器能让各平台运行同一份实现，但比编译后的代码慢好几倍。有了指令检查和打包器侧的燃料，
两个编译型引擎就能给出相同结果，因此不需要解释器。

### 接口（`vx1`）

- **导入**都在导入模块 `vx1` 中，模块名就是接口版本。新版本新增一个模块，绝不修改已有模块。
- **类型。** 只有 `i32` 和 `i64`。对象用句柄表示：阵营索引（`i32`）、类型句柄（`i32`，rules
  加载后的注册表索引）和对象稳定 id（`i64`）。过期句柄返回错误码，绝不触发 trap。
- **必需导出。**
    - `vx_abi_version() -> i32`；
    - `vx_init()`，挂载时运行一次；
    - `vx_io_buffer() -> i32`，变长参数和结果所用缓冲区的地址；
    - 各条目表，第一个是 `vx_ai_conditions(house, first, count)`，为每个已注册条件向缓冲区写一个结果。
- **静态注册。** 清单列出每个导出及其服务的 INI id 或保留编号；引擎在挂载时将该列表与模块导出核对。
  运行时不能新增钩子，所以钩子集合受 mod 摘要保护。
- **查询立即执行**，通过所属模块的读取 API 读取当前状态。
- **动作先缓冲。** 一批调用中的动作按顺序排队，批次返回后由引擎通过各自的所有者提交。
  触发 trap 或燃料耗尽的批次不提交任何动作。
- **代码位置。** 宿主端代码放在 `vera20k-core` 的 `src/sim/logic/`，与它所特化的解释器相邻，
  不依赖 `render`、`ui`、`audio` 或 `net`。

| 类别 | 例子 | 规则 |
| --- | --- | --- |
| 查询 | `house_money`、`house_power`、`house_count`、`super_ready`、`type_id`、`unit_health`、`cell_owner` | 只读，立即执行 |
| 动作 | `team_create`、`script_set_mission`、`trigger_fire`、`grant_super` | 先缓冲；都要经过该状态在引擎中的所有者；不允许直接写入 |
| 事件 | `on_unit_created`、`on_destroyed`、`on_timer` | mod 只注册用到的事件；引擎在固定的 tick 阶段回调 |
| 状态与随机 | `kv_get` / `kv_set`、`rand(lo, hi)` | 写入存档并参与哈希；随机数来自对局随机流 |

接口先只在低频挂点开放：AI 触发、脚本、地图触发、单位生成与死亡。伤害结算、移动这类逐单位、
逐 tick 的挂点，要等 20,000 单位、30 家的压力测试之后再开放。引擎的原生行为始终保留；
WASM 只接管 mod 注册的条目和事件。

### 原生能力保持原生

Ares、Phobos 等[能力](capabilities.md)不是 WASM 插件，也不计划做 `ares.wasm`。它们从内部改变原生
函数：钩进 gamemd 函数的中间、给对象添加状态、逐单位逐 tick 运行。做成插件就需要在几乎每个钩子处
开接口，还会成为引擎已移植行为的第二个所有者。它们仍是编译期特性（`cfg(feature = "ares")`），
移植进各自的原生所有者。mod 的清单声明它需要的能力，缺少这些能力的构建拒绝挂载它。

这些能力的文档决定范围：有哪些功能、读哪些键。文档不给出默认值、解析细节、钩子位置、随机数抽取、
计时器和功能之间的交互，而 mod 依赖所有这些，包括 Ares 的 bug。因此行为依据是 DLL 的指令，
加上对它所钩住的 gamemd 函数的原生移植，如 [ares.md](ares.md) 所述。

## 引擎加载

每个 vmod 在进程启动时挂载一次，排在所有原版 mix 和 `expandmd` 之前。

```
spawn.ini [Mods] -> 验证签名 -> 按依赖排序
  |- 数据区段:   解密 -> 条目 -> 内存中的 MixArchive
  |- 明文区段:   索引 -> 基于文件子区间的 MixArchive
  `- logic.wasm: 指令检查 -> 编译（桌面端缓存），常驻 -> 已注册的条目和事件

AssetManager 归档（优先级从高到低）:
  vmod 数据 > vmod 明文 > langmd.mix > ... > expandmd99..00 > ra2md.mix > ra2.mix ...
    -> 现有读取器，保持不变: INI 分层、SHP/VXL/HVA/TMP 解析器、
       图集、模拟资源目录
```

- **交接。** 启动器在 `spawn.ini` 中添加 `[Mods]` 区段，写入每个 mod 的 id、版本和摘要，
  且已按依赖排序。`open_startup_archives` 在 `langmd.mix` 之前挂载 vmod。先挂载的归档优先，
  因此 vmod 胜出。
- **归档。**
    - 解密后的数据区段成为内存中的 `MixArchive`。这需要一个接受条目的构造函数；
      `MixArchive::from_bytes` 已经能从内存构建归档。
    - 明文区段成为基于 `MixData` 子区间的 `MixArchive`：桌面端为文件的内存映射，
      浏览器端则把整个文件读入内存。
- **逻辑注册。** 清单列出每个编译出的或手写的导出，以及它服务的 INI id 或保留编号。
  加载 rules 时，在应用地图分层之后，每个注册表条目记录自己是原生执行还是通过导出执行。
- **散文件。** 原版允许游戏目录中的散文件优先于所有 mix（`CCFileClass::Open` 先查磁盘再查 mix，
  `0x00473D10`）。启用 vmod 时，改为 vmod 提供的文件名优先于散文件；否则玩家目录里一个旧的
  `rulesmd.ini` 就会覆盖 mod。这是对原版顺序的有意偏离，受 VeraX 控制。
- **生命周期。** `LoadFileFromMIX` 缓存（`0x005B40B0`）在整个进程期间存在，并保留首次命中结果，
  因此 mod 只在启动时挂载，不能在进程中途更换。桌面端已经是每局启动一个新进程
  （`vera20k -SPAWN`），浏览器版本在下一局之前也已经需要重新加载页面。
- **下游不变。** SHP/VXL/TMP 解析器、图集以及模拟使用的资源元数据（SHP 帧数、TMP 高度和地形类型、
  VXL 准入）保持原样。

## 多人对战、存档与回放

mod 列表及其摘要属于对局输入：不一致时房间无法开始，存档和回放也只能在 mod 相同时打开。

- **房间。** 房主选择 mod；房间携带每个 mod 的 id、版本和摘要。客户端从 mod 库下载缺失的 mod，
  摘要校验通过后才算就绪。
- **握手。** mod 摘要列表并入 rules 兼容性数据，与 rules 和地图摘要一起比较。目前
  `RulesCompatibility`（`src/rules/compatibility.rs`）只区分已编译的能力集。
- **rules 摘要。** 数据 INI 仍是普通 INI，因此现有 rules 摘要应该无需修改；需确认
  `multiplayer_rules_digest` 是在资源解析之后读取文件的。逻辑摘要也要并入，因为编译后的条目
  不再出现在 INI 中。
- **存档与回放。** 其元数据记录 mod 列表和摘要。mod 缺失或不匹配时拒绝加载，并指向正确的版本。
- **同步哈希。** 逻辑通过引擎状态起作用，且键值存储已包含在 `world_hash` 中，因此无需额外处理。

## 打包器：`vmod build`

`vmod build` 是一个命令行工具，把 mod 项目目录转换为签名的 `.vmod`。编译和检查在作者的机器上进行；
引擎只接受结果。它链接 `vera20k-core`，并使用引擎的读取器和解释器。

1. 读取 `mod.toml`：id、版本、依赖、保护规则。
2. 用引擎的解析器检查 INI 文件，报告引用了但不存在的类型和资源。
3. 规范化 INI 文件：先按原生方式拆行，再处理注释和空白；保留所有键及顺序。
4. 把逻辑部分编译为 IR，拆出骨架，并与原生解释器做等价性检查。
5. 编译手写逻辑（Rust SDK，`wasm32` 目标），与编译出的 IR 链接，用每次构建的随机种子混淆，
   检查指令集和导入列表，输出 `logic.wasm`。
6. 按保护规则对资源分类，并用 MIX 名称哈希替换文件名。
7. 数据区段：压缩，并用每次构建生成的密钥加密。
8. 写入明文区段：MIX 风格的索引和正文，索引经过加密。
9. 写入包含各区段摘要和逻辑导出的清单，并用作者私钥签名。

配套的 `vmod inspect` 只显示清单和摘要，不显示内容，供作者和 mod 库核对。

## 签名与安全

签名回答的是谁发布了包、包是否被改动；沙箱限制 mod 代码能做什么；内容指纹用来识别重新上传。

- **作者密钥。** 作者在本地生成 Ed25519 密钥对，并把公钥注册到 mod 库，与其 VERA20K 账户绑定。
- **验证。** 引擎在挂载前验证签名和每个区段的摘要。排位赛只接受在 mod 库注册过的公钥和摘要。
- **重新上传。** 提取后重新打包的包摘要会变，因此 mod 库改为比较内容：对每个规范化后的 INI 区段、
  每个资源和每个逻辑导出做哈希，按与已注册 mod 的重合度评分。
- **沙箱。** WASM 只能调用列出的导入；无法访问文件、网络或时钟。内存页数和每次调用的燃料都有上限。
- **自动下载。** 为房间下载的 mod 同样是代码：先验证签名，再检查指令集，之后才实例化。

## 阶段与验收

1. **容器与挂载。** vmod 格式、签名、加密数据区段、明文区段、数据 INI。
   门槛：同一个 mod 分别打包为 vmod 和 `expandmd` 时，得到相同的 rules 摘要，对局中画面相同。
2. **运行时与 AI 触发编译。** 桌面端的 wasmtime 与浏览器的 WebAssembly、指令检查、打包器侧燃料、键值存储；从 INI 编译
   `[AITriggerTypes]` 条件，带等价性检查和混淆；条件编号 ≥ 1000 用于手写导出。
   门槛：带编译触发的 mod 在桌面对浏览器的对局中保持同步，选出的队伍与其 INI 形式相同，
   且存档重新加载后结果相同。
3. **多人对战与分发。** 房间中的 mod 列表和握手、自动下载；存档和回放记录 mod；mod 库注册作者密钥
   并为内容做指纹。
   门槛：没有该 mod 的玩家加入时会获得它；版本不匹配时无法开始；提取后重新打包的内容会被标记。
4. **更多逻辑与接口。** 先是 `[ScriptTypes]`，然后是地图触发；事件；Rust SDK、打包器文档、示例 mod。

第 3 阶段之后，带编译逻辑的 vmod 可以在多人房间中使用；第 4 阶段按需扩展。
前两个阶段受 VeraX 能力控制，不影响原版构建。

## 风险与未决问题

主要接受的限制：修改过的引擎可以在挂载后导出数据 INI 和资源，GPL 分支可以运行所有 vmod。

风险：

- **修改过的引擎。** 解码后的数据 INI 和资源，改一行引擎代码就能写出。只有编译后的逻辑能抵御这一点，
  且抵御程度取决于混淆的强度。
- **GPL 分支。** 分支拥有全部接口。技术上无法阻止；VERA 的竞争力在于大厅、账户、天梯和 mod 库。
- **等价性漂移。** 原生解释器的改动会改变编译后的逻辑应有的行为。涉及解释器的引擎更新要对已注册的
  mod 重跑等价性检查，结果不同时提升逻辑接口版本。
- **跨接口开销。** 伤害结算之类的高频钩子可能在跨接口上花费过多，在浏览器的 JS 胶水上尤甚；
  需先进行 20,000 单位的压力测试。
- **引擎分歧。** wasmtime 与浏览器引擎必须给出相同判定。指令检查和打包器侧燃料去掉了已知的差异来源；
  第 2 阶段的门槛用桌面对浏览器的对局来发现其余问题。
- **名称枚举。** 需要枚举文件名的功能，例如地图列表和 `RULEMD*.INI` 选择器，无法配合哈希名称工作。
  第一版 mod 不携带地图。
- **接口版本。** 数据 INI 保留所有键，因此引擎更新无需重新打包，但 `logic.wasm` 依赖接口版本，
  接口必须保持向后兼容。

未决问题：

- [ ] 启用 vmod 时，vmod 文件是否应优先于游戏目录中的散文件？
- [ ] 数据区段的软上限定为多少？需要在浏览器中测量。
- [ ] `multiplayer_rules_digest` 是否在资源解析之后读取数据 INI？
- [ ] 哪些构造状态能让等价性检查覆盖 `condition_holds` 的每个分支？
- [ ] mod 库放在哪里：作为 ra20k.com 地图库的扩展，还是独立部署？
